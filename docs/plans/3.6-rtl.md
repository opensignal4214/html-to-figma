# Plan — 3.6 RTL (direction-aware text alignment)

Status: **shipped** (text alignment; flex-order deferred) · Roadmap 3.6 · Effort: S (scoped)

## Problem

`getComputedStyle().textAlign` returns the logical value `start`/`end` for
default text. `mapTextStyle` maps `start`→LEFT, `end`→RIGHT unconditionally,
which is wrong under `direction: rtl` — RTL `start` means the **right** edge. So
Arabic/Hebrew text (or any `dir="rtl"` block) currently aligns to the wrong
side in Figma.

## Design (scoped)

Make `mapTextStyle` **direction-aware** for the logical alignment keywords:

- `start` → `direction==='rtl' ? RIGHT : LEFT`
- `end`   → `direction==='rtl' ? LEFT : RIGHT`
- explicit `left`/`right`/`center`/`justify` are unchanged.

`cs.direction` is already available on the computed style; no new capture. This
is additive to behavior only for RTL + logical alignment; LTR output (incl. the
pricing-card baseline) is unchanged because `start`→LEFT / `end`→RIGHT still
holds when direction is ltr/absent.

## Explicitly deferred (separate follow-up)

**RTL flex/Auto-Layout order flipping.** Figma's primary axis is always
left-to-right, so representing an RTL row means reversing children *and*
flipping `primaryAxisAlignItems` — and it interacts with `*-reverse` (double
negation). That's intricate and error-prone; keep it out of this slice and
track it as a 3.6 follow-up. Text alignment is the most visible RTL defect and
is clean to fix now.

## Test plan (TDD)

1. Unit (`css-map.test.js`): `mapTextStyle({textAlign:'start', direction:'rtl'})`
   → `RIGHT`; `end`+rtl → `LEFT`; `start` (ltr/absent) → `LEFT` (baseline
   guard); explicit `right` unaffected by direction.
2. Baseline: pricing-card `tree.json` byte-identical (LTR).
3. e2e/preview: an RTL paragraph fixture aligns to the right; overlay confirms.

## Risk / rollback

Tiny, additive, LTR-unchanged. One revertible commit.
